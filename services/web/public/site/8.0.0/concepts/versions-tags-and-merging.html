Versions, tags and merging

For: Practising architects, Model Admin

How changes become part of a model, how you go back, and how several teams work on one model at once.

On this page
  • Every change has a history
  • Tags: moments you can return to
  • Working copies and merging
  • Read next

Every change has a history

In EA Explorer nothing is lost. A change to a model's content starts as your uncommitted change: only you and the model's Committers see it. A commit makes it part of the model for everyone, with a message saying what and why (Commit your changes). Every committed change keeps who, when, before and after, so any entity can be put back as it was (Roll an entity back to an earlier version) and any commit undone (Roll back a commit). Review before commit is what lets an organisation trust a model many people change.

Tags: moments you can return to

A tag names a moment in a model, such as "Baseline 2026" or "Before the merger" (Tag a model). Tags are what projects compare (baseline against target), what KPIs are kept at, and what you go back to if needed (Put a model back to a tag).

Working copies and merging

For larger work, a child model is a working copy that can be changed freely and merged back when agreed: the parent's admins review each change, accept or reject it, and merge it as one commit (Merge a child model back). Meanwhile the child can take the parent's newer changes (Take changes from the parent). This is how a project builds its target beside the live baseline without disturbing it.
