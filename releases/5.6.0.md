# EA Explorer 5.6.0: Release 5.6, backup and restore tested

Release 5.6 (16 Nov 2026; the owner: "Build 5.6"): **the backup and restore test** the owner set out, **job priorities**,
**updates and deployments from the published GitHub Releases only**, and **the restore drills** as documents with a PDF.

**Before updating:** take a backup (`.\eax backup before-5.6.0`). From 5.5.0 the update runs migrations 0098 and 0099
(job priorities: two tables; the version). A **clean rebuild** is needed: the API, the job runner, the operations
helper, the backup container, the screens and the eax command change (`.\eax clean-restart`). Then `.\eax test full`,
which now ends with the backup and restore test (it asks nothing).

## The backup and restore test (R5.6-B1)

The owner's test: "do an infra backup ... B1; create a project with some models; create content ... documents, custom
reports and custom views in various states, tags and all other kind of content; do an infra backup B2; restore B1: the
projects and models should be gone; restore B2: all content should now be checked including files using checksum".

- **`.\eax test backup-restore`** (also `.\eax test restore`, and last in `.\eax test full`): a test style of its own,
  **synchronous**. eax runs one command after another and waits for each: the backups and restores in the operations
  helper, the content through the REST API and MCP in the API container. No test container, no background task, no
  job queue. Each step is printed with its result; the first step that fails stops the test and says which and why.
- **On this installation, asking nothing**: it says first, plainly, that anything done meanwhile is lost. Then the
  **maintenance page goes on for everyone and everything in the background stops** (every recurring job, the scheduled
  backups, commands and updates; what misses a turn runs at its next one); both come back when it ends, whatever
  happened. Jobs the test itself needs (a project's folders in Documents) still run.
- **B1** (a random name), then **content of every kind**: a project and its models (entities, relationships, a drawn
  view, a child model with its own change, an uncommitted change, a tag), a KPI, a custom view, project steps, a key
  question, a stakeholder and a discussion, a Business Model Canvas, a document class with a document and its file,
  an ADR linked to an element, a dispensation, a discovery project with a source and a whole run (Found in, a skipped
  item), two test accounts with their roles, and a file in persist/ and in the import folder.
- **B2** (a random name). **B1 restored**: everything made is gone, and every table of every database and every file of
  every file set is as at B1. **B1 restored again**: the same fingerprint (S8). **B2 restored**: everything is back
  row for row, and **every database's rows and every file's checksum** are as at B2 (the documents, the certificate,
  the reports' home, the import and export folders, persist/ and the config file).
- **After B2**: the test's accounts sign in (S1); search finds the restored elements and the KPI is read (S4); a new
  element, a commit, a tag, a document and a new ADR numbered after the last all work (S5); no job ran twice and none is
  left running (S6); the document downloads with the checksum it was uploaded with (S7).
- **Refused before anything is touched** when the disk is short, saying how much is needed (S12). The scheduled
  clean-up never removes B1, B2 or a pinned backup (S14). No password, key or token in the report or the restores' logs
  (S13). The times of each backup and restore, the recovery time and the recovery point are in the report (S15).
- **When it fails after B1 was restored**, B2 is restored first, so the installation is as it was; the backups are kept
  and named. **When it passes**, the test's data and both backups (and the backups the restores took first) are removed.
- **The report**: work/tests/backup-restore-<time>/report.md and report.json, and Self-test › History.
- **It replaces the old restore suite** (R3.8): a self-test run no longer restores anything.

## Disaster recovery: eax-dr and eax-drill (R5.6-B2)

A **dr folder** that runs on its own, copied anywhere outside an installation (PowerShell and bash forms; nothing asked):

- **eax-dr** builds a whole environment from an infrastructure backup: give it the backup's folder, the folder to
  install into, the version and a copy of the env file. It checks the backup file by file against its checksums,
  downloads that published release from GitHub, puts the env file and the backup in place, builds and starts EA
  Explorer, restores everything with the maintenance page on, starts it again and runs the smoke test.
- **eax-drill** is the restore drill, automated: give it a running installation, a new folder for the DR copy and a
  temp folder. It checks the installation runs, makes test content, takes a full backup, shuts the installation down
  (containers removed; its data and images kept), copies the backup and env file into the temp folder, builds the DR
  copy with eax-dr in the new folder under its own Docker name (its own volumes) and restores it, then compares every
  table and file and the test content with before and runs the smoke test. The installation's folder and data are
  never touched; the DR copy is left running, and the report gives the recovery time and how to go back.
- **`eax dr-pack <folder>`** makes a DR pack in one command on the running installation: the maintenance page on for a
  few minutes, a **fingerprint** of every table and file, a full backup, then the pack: the backup, `VERSION.txt`, the
  env file, `fingerprint.json`, the DR tool, `RESTORE.txt` and `PACK.sha256` (a checksum of every file).
  **`eax-dr -Pack <pack> -Install <folder>`** checks every file of the pack first and, after the restore, compares every
  table and file with the fingerprint: proof that everything came back.
- **Disaster recovery: the DR pack and the DR tool** (Documentation › Administration and operations, with Download
  PDF): making a DR pack, taking it to another server, rebuilding with eax-dr, the checksums and the fingerprint
  explained, rehearsing with eax-drill, and every command and option in full. The monthly restore drill now uses
  eax-drill and eax dr-pack. Long command lines wrap in the PDFs.
- `eax drill ...` holds the steps they ask of eax (never from the web).

## Job priorities (R5.6-Q2)

- Every kind of job has a priority: **high** (what people ask for, the alert checks), **normal**, or **low** (the
  recurring data quality checks, digests and reminders, trends and samples, background loads). The job runner takes the
  highest first.
- **When the queue is too full** (more than 20 waiting, or the oldest waiting more than 10 minutes; both settings), a
  waiting low-priority recurring job misses its turn: its next run does the work. After five skips in a row it runs
  anyway. A job a person asked for is never skipped. Each skip is counted on **System Admin › Jobs › Priorities** and in
  the stuck-jobs alert's message.
- Change a kind's priority on the same page (Super Admins and IT Admins).

## Updates and deployments from GitHub Releases (R5.6-U1, U2)

- The repository is **https://github.com/gauravvermaea/EA-Explorer**, for the releases and the code.
- **System Admin › Updates**, **`.\eax update`**, **Sites › Deploy EA Explorer**, **`.\eax deploy`** and the installers
  offer only the repository's **published GitHub Releases**, newest first, with their notes, and only newer than the
  installed version: never the main branch, never a draft, never a tag with no published release. RC adds the
  pre-releases. The **Latest** channel is gone.
- Updates and Deploy show the releases in a **drop-down** with the chosen release's notes.
- When GitHub cannot be reached, or its limit on calls without a sign-in is reached, they say so and offer nothing.

## Fixed while testing it

- An infrastructure backup failed with only "pg_dump: detail: Query was: ..." when a report view was made again while
  it was read (a metamodel change, or the report views' own refresh). Each database's dump is now tried three times,
  20 seconds apart, and a failure names the database and pg_dump's own error.
- The backup and restore test's fingerprint stopped after the last table on an installation with no database on a
  server of its own.
- Every start marked every built-in view as modified (the report catalogue was written again whether or not it had
  changed), so a restored installation never looked exactly like its backup. A built-in view is now written only when
  something in it changed.
- Adding a KPI through the MCP tools always failed (the fields were sent under the wrong names).
- The backup and restore test took the Keycloak realm's name for a secret, and compared the start-up status, which
  every start writes again.
