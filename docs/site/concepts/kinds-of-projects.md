## Why projects come in kinds

Architecture work is always done for a reason, and the reason decides the work. Documenting how things are today
needs catalogues and diagrams but no target; a cloud migration needs a target, waves and a roadmap; a merger needs two
current states side by side. A **project template** sets a project up for its reason: which ADM phases and steps it
runs, which deliverables it produces, which models it needs and who signs off. You can change everything afterwards;
the template is a good start, not a cage. See [[start-a-project-from-a-template]].

## The kinds and their goals

| Kind | The goal |
| --- | --- |
| Transformation | Move from today's architecture to a target through intermediate states, with the gaps and a migration roadmap |
| Document the as-is | A trustworthy picture of how the enterprise works today; no target |
| Create a new product | Design a new product or service: business model, value, capabilities and the architecture to deliver it |
| Copy a model for new reports | New views and reports on a copy, leaving the original untouched |
| Copy, update and merge back | Update a model's content in a working copy and merge it back when agreed |
| Scenario planning | Compare two or more possible futures from the same starting point, before choosing |
| Regulatory or compliance change | Turn a regulation's obligations into requirements, find the gaps against controls, prove compliance |
| Technology refresh or cloud migration | Move technology to new platforms in planned waves |
| Application rationalisation | Decide for each application: keep, invest, migrate or retire |
| Operating model redesign | Redesign organisation, roles, processes and capabilities together |
| Capability-based planning | Plan change by capability: current and target maturity, the gaps, the roadmap |
| Architecture assessment or health check | Judge existing models for quality, principles and risk; change nothing |
| Solution architecture for one initiative | The architecture of one solution inside the enterprise picture, merged back after go-live |
| Due diligence, merger or acquisition | Two current states, their overlaps, and a combined target |

## Choosing

Start from the question the sponsor needs answered. If nothing changes, it is documentation or an assessment. If one
future is already chosen, it is a transformation, migration or solution architecture. If the future is still open, it
is scenario planning. If an outside rule drives it, it is a compliance change. When in doubt, a blank project and the
[[the-adm|ADM]] phases you need are always possible ([[start-a-blank-project]]).
