## Start and stop
: cleanup, clean-restart and clean-run DELETE data. To stop without deleting anything, use stop.

### up|run [service...] [--wait-all]
> Starts EA Explorer. Keeps the databases, documents and settings from last time.
The everyday start; run is the same as up. It builds our images, pulls the others and starts in two tiers (D255):
the core first (sign-in, the database, the API and the screens; you can sign in when it says ready), then Reports,
Documents, draw.io and the sample data in the background. Before starting it copies what is new or changed in the
industry pack sources into library/industry-packs (packs auto; quick when nothing changed), and as it starts it loads
the packs and the documentation into Documents and the library, and prepares the test runner in the background
(everything you need, nothing to run by hand, D584). Afterwards it prints the addresses and, on a laptop, the logins.
  --wait-all     start everything and wait until all of it is up (also on debug, restart and the clean-* commands).
  service...     start only those services and what they need: "up api proxy" starts the database, the API and
                 nginx only (about 1 GB); the API is then at https://localhost/api/docs.
Running up on a running installation is an upgrade: everyone sees the maintenance page until it has finished.
$ {eax} up
$ {eax} up --wait-all
$ {eax} up api proxy

### stop|down
> Stops EA Explorer (removes the containers). Keeps all data: databases, documents, settings, backups.
Nothing is deleted: the Docker volumes and the work folder stay, so the next {eax} up carries on where you left off.
Use it before shutting the computer down, or to free memory. down is the same as stop.
$ {eax} stop

### restart [--wait-all]
> Stops EA Explorer and starts it again (stop, then up). Keeps all data.
Use it when something is stuck. A maintenance page or a paused background left behind is taken away between the
two, so EA Explorer comes back open. Each step writes its own log. To start again with empty databases, use
clean-restart instead.
$ {eax} restart

### cleanup [--all] [--yes] [--certificate]
> Stops EA Explorer and DELETES the work folder (config, logs, backups); --all: the databases too.
Deletes: the config file, every log, the laptop data folders, and every backup and restore log. With --all it also
deletes the Docker volumes, so the databases and documents start empty. Keeps: the local certificate
(work/data/tls; --certificate deletes it too) and work/tools. Asks you to type yes unless --yes is given.
$ {eax} cleanup
$ {eax} cleanup --all

### clean-restart [laptop|server] [--certificate|--password] [--wait-all]
> Stops EA Explorer, DELETES everything (databases included) and starts fresh. Does not ask.
For testing a new version: stop (down), then cleanup --all --yes, init and up. Fetches the current base images first
(with their security fixes) and rebuilds our images on them, then starts with empty databases and the sample data, the
industry packs, the documentation and (in the background) the test runner: nothing else to run before testing. The
trusted certificate and persist/ are kept. --certificate or --password: how the services sign in (given to init);
without either, the choice made before is kept.
$ {eax} clean-restart
$ {eax} clean-restart laptop --certificate
$ {eax} clean-restart --wait-all

### clean-run [laptop|server] [--certificate|--password] [--wait-all]
> DELETES everything (databases included), then starts fresh: cleanup --all, init, up. Does not ask.
Like clean-restart, it fetches the current base images first and rebuilds our images on them; --certificate or
--password as for clean-restart.
$ {eax} clean-run
$ {eax} clean-run server

### maintenance on|off|status|clear [--force]
> Shows or hides the maintenance page; status and clear: what a cut-off backup or DR run left.
Served by the proxy. Restores and up (an upgrade) switch it on and off themselves. When a backup, a restore, the
backup and restore test, the drill or a DR pack was cut off (a crash, a closed window), status shows what it left: the
maintenance page, a restore's record that it is under way, the background paused. clear removes all three, so EA
Explorer opens again and its recurring jobs run; it refuses while the backup container is still running a backup or a
restore (--force clears anyway; nothing is stopped either way).
$ {eax} maintenance on
$ {eax} maintenance off
$ {eax} maintenance status
$ {eax} maintenance clear

## Status and logs

### status [problems]
> Lists every container, the disks, then every problem with its error code and what to do.
First the release and its build ("EA Explorer 1.0.0, build 4f2a9c1", as at the top left of the screens). Stopped
containers are listed too. Then the file systems: Docker's disk, the work and backups folders, and this
computer's drive (size, used, free). Then the problems: each container not running well, each service whose
health check fails and each open alert, with its error code (EAX-AREA-NNN, for example EAX-AUTH-001) and what
to do. The error guide lists every code. "problems" lists the problems only. Changes nothing.
$ {eax} status
$ {eax} status problems

### sonar open|close
> SonarQube's own pages with the last scan's results, on this computer only; nothing is scanned.
open starts SonarQube with its pages at http://localhost:9000 (EAX_SONAR_PORT to change the port), reachable from
this computer only, and waits until it is ready; sign in as admin, the password is in work/tests/sonar/admin. It
shows the last scan; eax test sonar makes a new one. close removes SonarQube again (its data kept); eax down
removes it too. Changes nothing of EA Explorer.
$ {eax} sonar open
$ {eax} sonar close

### errors [<code-or-words>...]
> What an error code means, its usual cause and what to do; no words: every code.
Every problem EA Explorer finds has a code EAX-AREA-NNN: in eax status, System Admin health and alerts, the
screens' error messages, the API's answers and the logs. Give a code for what it means and what to do, an area
(AUTH, BAK, DB...) for its codes, or words to search for. The same list makes the error guide on the website and
in the printed troubleshooting guide. Changes nothing; needs no containers.
$ {eax} errors EAX-AUTH-001
$ {eax} errors BAK
$ {eax} errors backup

### url
> Prints the addresses to open (and the logins on a laptop).

### logins [--admins] [--yes]
> Shows the user names and passwords on the screen: every one, or with --admins the admin accounts only.
--admins: EA Explorer's Super Admin, Keycloak's administrator, the break-glass account (for when Keycloak is down) and
Jenkins' administrator when Jenkins is on. On a laptop it shows them at once (and after eax up). On a server it asks you
to type YES first (--yes: no question, for a script you run yourself), and only works for whoever can read the config
file. The passwords are never written to a log; on a server the audit log keeps who looked and when (D975). Save the
admin and break-glass passwords in your password manager.
$ {eax} logins --admins
$ {eax} logins

### logs [service|backup|clean] [--older-than N] [--yes]
> Follows the logs of every container, or of one; or backs up or cleans the logs kept on disk.
Ctrl+C stops following; nothing is stopped. Every container's log is also kept on disk, one file a day (logs/, or the
folder EAX_LOGS_DIR names), across clean-restart and updates (R2.32). `logs backup [tag]` zips those and eax's own
logs (work/logs) into work/backups/logs; `logs clean` deletes them and the log backups when older than N days (default
14 on a laptop, 90 on a server; also every night, System Admin > Settings "Delete logs older than"), asking first
(--yes skips it) (R2.30). With logs backup, --outside-work puts the zip in the kept-backups folder beside the logs
folder (outside work/, so a clean-restart keeps it) and --then-clear deletes the container logs and the web log once
they are zipped (clean-run and clean-restart do both).
$ {eax} logs
$ {eax} logs api
$ {eax} logs backup before-upgrade
$ {eax} logs clean --older-than 30 --yes

### diag
> Saves a diagnostics report into this run's log: the file to send when asking for help.
Docker versions, memory and disk, image settings, every container's state, the last 300 log lines of each
container, and the compose configuration (passwords masked).
$ {eax} diag

### footprint [label] | --watch [minutes] [label] | --history [days]
> Measures how much each container takes and keeps it in work/footprint, beside the measurement before.
Image size, the container's own disk, its volumes, memory and CPU now, and how long it took to start (to healthy).
work/footprint/latest.md is the table, with the change since the one before in brackets: measure before and after a
change (label says which). Also System Admin > Footprint (R2.22). Changes nothing.
--watch samples every container's memory every 15 seconds (10 minutes unless given): each one's lowest, average and
peak, the whole installation's peak beside the guide of 10 GB (EAX_MEMORY_TARGET_MB; not a limit) and whether the
Docker host paged (swap). Kept in work/footprint/latest-memory.md. Every self-test run is watched the same way on its
own (memory.md in its folder). Release 3.5 (R3.5-M1).
$ {eax} footprint
$ {eax} footprint after-slim-images
--history shows the resource history (1 day unless given): a sample every 15 minutes, taken all the time, while
people work and while the self-test runs: memory, CPU, disk and the database's cache of every container, the peaks
and paging. The interval, how long it is kept, CSV and deleting: System Admin > Footprint (R3.5-M8).
$ {eax} footprint --watch 30 at-rest
$ {eax} footprint --history 7


### measure [--restart|--clean-restart] [--full|--no-full] [--unattended] [--use-minutes N] [--from N] [--yes]
> Measures how much memory EA Explorer needs, in one go: each step run and checked, then a summary.
Steps: a restart (only when asked), memory while it starts and loads (20 minutes), a snapshot, the smoke test, at rest
(10 minutes), in use (20 minutes; on a laptop the browser opens for you to use it), the full test while you use it,
then one summary: each situation's peak and average, paging and the biggest containers, beside the guide of 10 GB
(not a limit). Kept in work/footprint/measure-<time>.md. Safe on a running installation and on servers:
--clean-restart (DELETES everything) is refused except on a laptop, and on a server the full test runs only with
--full (its restore part asked first); --no-full leaves the full test out. --unattended: nobody there (no browser; no in-use step on a laptop). A step
that fails stops it with the command to carry on (--from N). Release 3.5 (R3.5-M1).
$ {eax} measure --clean-restart
$ {eax} measure
$ {eax} measure --from 4 --yes
$ {eax} measure --from 5 --no-full
### ticket [list [open|all|<status>]|show REQ-n|comment REQ-n <text>|status REQ-n <status> [note]]
> The service desk's requests: every team's, from the command line (admins).
People ask for things from the service catalogue (Service desk in the menu; R5.11). list: the open requests (or all,
or one status), overdue said; show: one with its details and history; comment and status act as "eax", recorded in
the request's history. The statuses: in-progress, waiting-requester, done, declined.
$ {eax} ticket
$ {eax} ticket show REQ-12
$ {eax} ticket status REQ-12 done "access given"

### jobs [list|history [N]|cancel|kill|up|down <id>|clear-stuck [--restart]|restart|delete-history [--older-than DAYS]|slots [<work> <scheduled>]]
> The background job queue: what runs, what waits, what is stuck; cancel, kill, reorder (admins).
As System Admin > Running > Jobs (R5.30 to R5.34). list: what is being worked on and waiting, stuck ones marked, and
what to do; history: the newest finished; cancel takes a waiting job off the queue, kill asks one being worked on to
stop (its work ends when the job runner restarts; a second kill marks it stopped at once, for a job no runner has any
more), up and down change the order; when the job runner restarts, jobs it left are marked stopped; clear-stuck kills every stuck one
(--restart then restarts the job runner); delete-history deletes finished jobs; slots shows or sets each API
server's job slots (taken at the next restart). Nothing is killed or restarted unless asked. Every action audited.
$ {eax} jobs
$ {eax} jobs kill 609
$ {eax} jobs clear-stuck --restart
$ {eax} jobs delete-history --older-than 7
$ {eax} jobs slots 6 2

### dev check [--quick] [--web]
> The first thing to run before changing EA Explorer: lint, tests and the documents' cross-checks.
For a developer (or another AI) taking the work over (R5.16): ruff, pytest in services/api (--quick: stops at the first
failure), the decisions numbered once each, help.txt ASCII, and the handover documents there; --web also
builds the screens. Nothing is installed; without ruff or pytest on this computer, lint and tests run in the test
runner (Docker) on this folder. Then read docs/handover.md.
$ {eax} dev check
$ {eax} dev check --quick --web

### estimate --users N --models N [--size small|medium|large] --projects N [--documents N] [--override FILE] [--json]
> The server sizing estimate: RAM, CPU and disk, per container too. A best estimate, it says so.
For a server (or a container platform) before it is made: people at once, models and their size, projects and the
documents each, what is switched on (--no-reports, --no-documents, --no-mcp, --no-discovery), backups kept (--backups N), headroom (--headroom,
0.3) and a platform's node (--node-gb, --node-cores). It answers the server's RAM, cores and disk (a year on), each
container's memory to reserve and its limit, the copies to run, the settings and the nodes, with its assumptions. It
needs nothing running. --override FILE writes a compose override with the limits (R5.19; System Admin > Sizing).
$ {eax} estimate --users 50 --models 30 --size medium --projects 40
$ {eax} estimate --users 300 --models 100 --size large --projects 200 --override sizing.yml

### optimise [report|last]
> The optimisation report: what to change to run lighter, with the evidence; nothing changed here.
EA Explorer measures itself on the 1st of every month (and when asked): the server's memory and CPU, models and
projects not opened or changed for 180 days (a setting), old self-test runs, Docker's build cache, history from before
a model's last tag, and the database check. Each suggestion has its evidence, what it saves, its risk and how to undo
it; it is applied on System Admin > Optimisation, for a whole model or project, by the person who decides it (R5.1).
report: measure now and print; last: the newest report.
$ {eax} optimise
$ {eax} optimise last

### db [check|integrity|tidy|compact|clear|locks|cancel|end] [DATABASE|PID] [TABLE] [--dry-run] [--fix] [--yes]
> Database maintenance: every database checked and tidied, as System Admin > Database maintenance.
check: what needs doing in every database, in plain words (swollen tables and indexes, stale statistics, unused,
duplicate or invalid indexes, the transaction age, connections, long transactions, the cache, sequences near their
limit, tables with no primary key, replication). tidy: what check finds, done without locking a table (VACUUM,
ANALYZE, REINDEX CONCURRENTLY); it runs by itself every night in the window (01:00 to 05:00 by default). compact: VACUUM
FULL of one table, which locks it while it runs (asked first). clear: the keep-for rules now. locks: who blocks whom;
cancel or end a session (asked first). Nothing runs during a backup, a restore or a self-test (R5.12). integrity:
every database's indexes, tables, constraints, sequences and newest records checked, nothing changed; --fix: the safe
fixes too, after a backup (the maintenance page up while it is taken) (R6.6.1).
$ {eax} db check
$ {eax} db tidy --dry-run
$ {eax} db locks

### databases
> Lists every database EA Explorer uses: what it holds, where it lives and whether it answers.
Each has its own setting in work/eaexplorer.env: empty = the shared PostgreSQL; set one to move that database to a

A database of its own gets its tables at the next start (eax up). `copy tests` brings the self-test runs made
before it moved (R2.28). `speed` times how the database compares text, and lists where the code does (R2.52).
$ {eax} databases
$ {eax} databases copy tests
$ {eax} databases copy operations
$ {eax} databases speed

### persist [list|delete] [<item>] [--all] [--yes]
> Lists what persist/ holds, or deletes an item of it (or everything) for good.
persist/ survives every reset by design: the schedules, the banner, the Self-test settings, the safety backups taken
before a command that deletes everything, the reset-survival results. A deleted settings file falls back to its

$ {eax} persist

## Backups and restores

### backup [tag]
> Takes an infrastructure backup now: every database, the document files, the certificate and config.
Also the release and image versions. Into work/backups/infrastructure (D216, D226). The maintenance page is on and the
background paused while it runs, once what the background was doing has finished (nothing is killed; D721).
$ {eax} backup
$ {eax} backup before-upgrade

### backups [words]
> Lists every backup (infrastructure and application); with words, only the ones that match.
Words are looked for in the tag, name and maker.
$ {eax} backups
$ {eax} backups before-upgrade

### restore [name|tag|latest] [--what full|app|app+data|db|files] [--yes]
> Restores an infrastructure backup. Asks what to restore, then for RESTORE to confirm.
Unless --yes is given. By name, by tag (the newest with it) or latest (the newest good one); without one it lists them to choose from.
  full       everything
  app        the config file
  app+data   the config file, the repository and document databases and the document files
  db         every database
  files      the document files and the certificate
A backup of the current state is taken first; nothing live changes until all is restored cleanly; it can be run
again. Works when the console is down (starts db, backup and ops).
$ {eax} restore latest
$ {eax} restore before-upgrade --what db

### restores
> Lists every restore (infrastructure and model) with its status.

### restore-log <id>
> Shows a restore's whole log (also in work/backups/restores/<id>).
$ {eax} restore-log 12

### delete-backup <name>
> Deletes an infrastructure backup (unpin it first if it is pinned).

### delete-restore <id>
> Forgets a finished restore and its log.

### stop-backup
> Stops the backups running; the partial backup is deleted. A restore cannot be stopped.
Infrastructure backups stop at once; application backups after the model they are on.

### app-backup [tag] [--models <names>] [--projects <names>]
> Backs up every model now (an application backup), into work/backups/application.
Every model and every project with its documents, and the organisation part. With --models (names or ids, separated by
commas) only those models, and with --projects only those projects beside them. Each file is read back and checked as
soon as it is written (D968): a file that does not check out is not kept, and the backup says so. The last lines say
the run's name (Run: ...), which check-backup, restore-model and restore-app take.
$ {eax} app-backup month-end
$ {eax} app-backup before-workshop --models "Protea Insurance (demo estate)" --projects "Protea Claims Transformation 2028 (sample)"

### model-backup <model> [why]
> Backs up one model now, as its Model Admin does on the model page.
The model by its name (in quotes when it has spaces) or its id. The file goes in work/backups/application/models/<model
id>/ and is checked as soon as it is written. The last lines say the file (File: ...), its SHA-256 and the command that
restores it. Needs the api container running (D970).
$ {eax} model-backup "Protea Insurance (demo estate)" before-merge

### restore-model
> Restores one model from an application backup, as a new model or over itself.
Lists the backups and the models in them to choose from. Needs the api container running. Without questions: the
backup's run and the model's backup file, then --new <name> (a new model of that name) or --over (over itself).
From one of the model's own backups (made by model-backup or on the model page): model <model> <file>. From a file
brought from elsewhere (in work/backups/application/uploaded): uploaded <file>. The file is checked first: a damaged
file, or one changed since it was made, is refused and nothing changes (D968).
$ {eax} restore-model 20261128T200000Z-month-end protea-insurance-1a2b3c4d.eaxbackup.zip --new "Protea (restored)" --yes
$ {eax} restore-model model "Protea Insurance (demo estate)" 20261128T201500Z-before-merge.eaxbackup.zip --over --yes

### project-backup <project> [why]
> Backs up one project now, with its models and the latest version of each document.
The project by its name (in quotes when it has spaces) or its id. The file goes in work/backups/application/projects/
<project id>/ and is checked as soon as it is written. The last lines say the file (File: ...) and the command that
restores it. Needs the api container running (D970).
$ {eax} project-backup "Protea Claims Transformation 2028 (sample)" end-of-phase-B

### restore-project <project|run> <file> [--new <name>] [--over] [--yes]
> Restores a project from a backup file: as a new project (the default) or over itself.
The file is one of the project's own backups (the project, then the file project-backup named) or a project in an
application backup (the run, then the file). As a new project it gets new ids and the name given; --over puts the
project back as it was, its documents too. The file is checked first; asks RESTORE to confirm unless --yes. Its
repository is built and its documents put back before it ends (Documents must be running) (D970).
$ {eax} restore-project "Protea Claims Transformation 2028 (sample)" 20261128T201500Z-end-of-phase-B.eaxproject.zip --new "Protea (restored)"

### check-backup [latest|all|<run>|<tag>|<file>]
> Checks backups: each zip file, its fingerprint and what it holds. 1 when any is not right.
Each file is opened and every member's checksum read; its fingerprint (the SHA-256 of every member, written into it
when it was made) compared; a model backup's package read and counted, a project backup's rows, models and document
files counted. An application backup's files are also compared with the SHA-256 its manifest gives. latest (the
default): the newest application backup; all: every backup there is; or a run, a tag, or a file's name. Reads only,
changes nothing (D968).
$ {eax} check-backup
$ {eax} check-backup all
$ {eax} check-backup 20261128T201500Z-before-merge.eaxbackup.zip

### restore-app [run|tag|latest] [--yes]
> Restores every model of an application backup, each over itself (each backed up first).
Models no longer there are made again; newer models stay as they are. Needs the api container running.
$ {eax} restore-app latest

### schedule [list|add <name> [when] [--off] [--no-backup] [--keep N] [--banner] [--confirm <name>] -- <command>|demo-reset [--at HH:MM] --confirm <name>|on|off|remove|run <id>]
> Scheduled eax commands: a cron in the platform, e.g. a demo that resets itself every night.
The same schedules as System admin > Command centre > Schedules, kept in persist/schedules.json, which no reset
deletes (D558, D559); the operations helper starts what is due, in the installation's time zone (EAX_TIMEZONE). When:
--at HH:MM (every night, the default), --weekly <0-6> (0 Sunday) with --at, --hourly <minute>, --once
YYYY-MM-DDTHH:MM or --cron "<minute hour day month weekday>". A command that deletes everything (clean-restart,
clean-run, cleanup) needs --confirm with the installation's name, once; it takes a safety backup first unless
--no-backup (the newest --keep N, default 3, kept in persist/safety-backups/). --banner tells everyone when the demo
resets. A run missed while the machine was off runs once if found within the hour; one due while another command runs
waits up to 30 minutes. Every run is in the Command centre's History.
$ {eax} schedule list
$ {eax} schedule add "Nightly backup" --at 01:30 -- backup nightly
$ {eax} schedule add "Weekly smoke test" --weekly 1 --at 06:00 -- test smoke
$ {eax} schedule demo-reset --at 02:00 --confirm demo-laptop
$ {eax} schedule off a1b2c3

## Updates

### sign [keygen [<file>]|trust <file.pub>|<version> --key <file> [--folder <path>] [--out <folder>]]
> Signs a version your organisation checked, so installations install only signed ones (optional).
The project does not sign its releases (R5.10); an organisation that wants to sign: keygen makes a key pair once (kept
by its release or security team, never on an installation; ssh-keygen asks for a passphrase); trust adds the public key
to an installation (persist/keys/trusted); <version> --key writes <version>.manifest (every file with its SHA-256) and
its signature into persist/keys/signatures (or --out, or the shared folder EAX_SIGNATURES_DIR). Copy both files to
each installation. From then on update refuses a version that is not signed, does not verify or whose files differ,
before anything changes. With no trusted key nothing changes. Needs ssh-keygen (OpenSSH: Windows 10+, Linux, macOS).
$ {eax} sign keygen
$ {eax} sign trust ~/.eax/eax-release-signing.pub
$ {eax} sign 5.0.0 --key ~/.eax/eax-release-signing

### verify <version> [--folder <path>]
> Checks a version against its signature and the trusted keys, as update does.
OK when it is signed by a trusted key and every file is as signed; REFUSED with why otherwise (exit code 1).
$ {eax} verify 5.0.0

### images [check] [--no-tell]
> Every image EA Explorer uses: the one here, whether a newer one is published, its fixable findings.
For our own images, the image each Dockerfile builds on; for the others (PostgreSQL, Keycloak, Superset...), the image
itself. Each is compared with the one published now under the same name (read from the registry, nothing downloaded),
with the fixable high and critical findings of the last security test. Nothing is changed: to take the newer images,
clean-restart (it fetches them and builds on them), then test full. A schedule runs it on the first day of every third
month (System Admin > Command centre > Schedules) and tells the Super Admins and IT Admins when something is newer
(R9.12); --no-tell does not. The report: work/images/check-<time>.md.
$ {eax} images

### update [--status] [--retry] [--channel prod|rc] [--to <version>] [--at <time>] [--url <link>] [--yes]
> Moves to a newer published GitHub release: a full backup first, then one release at a time.
Without options it is guided: it shows the installed version and the channels, lists the published releases above the
installed one (forward only; never the main branch) with their release notes, and asks which one, now or at a time, and
to type YES. Prod (the published releases) is always offered; RC (the published pre-releases too) only once enabled in
System admin > Updates. When GitHub cannot be reached, or its limit on calls without a sign-in is reached, it says so
and offers nothing. First a full backup (every database, every file, the config file and the code as it is, local
changes included; pinned), then the maintenance page while each release on the way is built here, started and checked.
A failed step stops and asks: --retry runs it again, or roll back. The update runs in its own updater container, so it
carries on while EA Explorer restarts. --status shows the installed version, the update running, the schedule and the
history. --url sets the repository link (EAX_UPDATE_GIT_URL). --at 22:00 (or a date and time) schedules it; signed-in
people see a banner beforehand. Also on System admin > Updates (Super Admins and IT Admins).
$ {eax} update
$ {eax} update --status
$ {eax} update --channel prod --to 0.20.0 --at 22:00
$ {eax} update --retry

### rollback [--yes]
> Back to the version before the last update: its code and its pre-update backup put back.
Work done since the update is lost; the current state is backed up first and kept. The failed version is marked in the
history. Asks you to type YES unless --yes is given.
$ {eax} rollback

### packs [auto|source [folder...] [--clear]|load [folder]|reload|status|ocr [--clear]|collect [source...]]
> The industry packs: the books, workbooks, metamodel Excel and PowerPoints on the library's Pack tab.
Nothing to run by hand (D584): every up, run, restart, clean-restart and clean-run copies what is new or changed in the
pack sources into library/industry-packs first (packs auto; quick when nothing changed; nothing to do when no source
folder is there), and EA Explorer puts them into Documents as it starts (new or changed files only, by checksum; files
marked not for AI use are never loaded; the start-up status shows "Industry packs loading n of N"). The pack sources:
persist/settings.json (set with packs source, kept across resets), else EAX_PACKS_SOURCE in the config (several
separated by ;), else Enterprise_Architecture\Industry Specific Guidance and Sample_Repo (the metamodels and views) in
your home folder. collect (optional) copies them now; the "complete set" zips are opened, the same file kept once,
files over 50 MB split into parts below 45 MB (no Git LFS). load (or reload) puts them into Documents now; load
<folder> loads another folder on this computer. status shows each industry's pack. ocr shows the OCR jobs waiting in
Documents (after a clean restart it reads every page of the pack files as a picture, an hour or more on a laptop, though
their text is already there); ocr --clear deletes them: the documents, their text and search stay. See
docs/industry-packs.md.
$ {eax} packs status
$ {eax} packs ocr
$ {eax} packs ocr --clear
$ {eax} packs source "D:\Packs\Industry Specific Guidance" "D:\Packs\Sample_Repo"
$ {eax} packs source --clear
$ {eax} packs load "D:\More packs"

### import [source|--all] [--as user]
> Takes the files other systems dropped in their delivery folders; each waits for review in the screens.
Without a source it lists every import source (a model's Import and export tab > Deliveries), its folder and how many
deliveries wait. With a source (its name, folder or id) or --all it takes the files in the source's folder in the
API's import folder, deliveries/<model>/<source>/incoming (the eax-imports volume, or EAX_IMPORT_DIR, which IT may map
to SFTP or a share). A CSV set with master.csv becomes one delivery; each workbook, .zip or CSV one each. Each is
previewed, then a Committer accepts or declines it on the model's Deliveries tab. --as names who took them (the log).
Needs the api container running. The formats: docs/import-formats.md.
$ {eax} import
$ {eax} import "Configuration database"
$ {eax} import --all

## Settings and services

### dr-pack <folder>
> A DR pack: backup, version, env file, code and the DR tool, with checksums and a fingerprint.
On the running installation, asking nothing: the maintenance page on for a few minutes, the fingerprint of every table
and file, a full backup, the page off; then into <folder> (new or empty, outside the EA Explorer folder): backup/<name>/,
eaexplorer.env, VERSION.txt, code/ (the code as it runs here, with CODE.sha256), fingerprint.json, the dr folder and
RESTORE.txt, and PACK.sha256 with every file's checksum, checked. On the new machine dr/eax-dr -Pack <folder> -Install
<folder> checks the pack, rebuilds EA Explorer from the pack's code (no GitHub) and compares every table and file with
fingerprint.json. The pack holds every password and all the data: keep it safe, away from this machine.
$ {eax} dr-pack D:\ea-dr-pack-2026-11-16

### drill [info|running|quiet on|off|fingerprint <file>|backup|take <name> <folder>|shutdown|restore <name>|signin|compare <a> <b>|code <folder>]
> The steps dr/eax-drill and dr/eax-dr ask of eax (R5.6-B2): you run those, not this.
dr/eax-dr builds an environment from a backup (backup folder, install folder, env file, and the code: a copy, or a
version from GitHub). code <folder> copies this installation's code, as it runs, with CODE.sha256. dr/eax-drill takes a
running installation, a new DR folder and a temp folder: a backup copied straight out of EA Explorer (take), the
installation shut down (containers removed, data and images kept), a copy built from its own code with eax-dr under its
own Docker name and restored. It fails only when the restore cannot be done or nobody can sign in (signin: Keycloak signs
its admin in and counts the people, the API answers); the key items compared are warnings. Each step here answers one
line of JSON; shutdown removes the containers only. Never from the web. Asks nothing. work/compose-project, when there,
is this installation's own Docker name.
$ {eax} drill info

### secrets [show|rotate|set|fill|push|pull|schedule] [KEY] [--due] [--all] [--restart] [--at TIME] [--to|--from file:PATH] [--by WHO]
> The passwords and keys: their ages, rotating them, and a copy in a file outside the installation.
Every password and key lives in work/eaexplorer.env and reaches each container as a file of its own (Docker secrets,
R6-F1), never as an environment variable. No key vault and no cloud service is used (D744, D746).
  show           every one by name (never its value): how it changes, when it last changed, when it is next due.
  rotate KEY     a new value now: a database login is changed in the database too, a sign-in client's secret in
                 Keycloak too; the services that use it are made again (a few seconds each).
  rotate --all   every one eax can rotate, in one go, behind the maintenance page: the background is paused and
                 waited for first (at most half an hour, else nothing changes); the services made again once at the
                 end, then the page comes down. What needs a person is listed, never changed. One rotation at a time.
                 --restart: EA Explorer restarted afterwards (Jenkins' Rotate all does this; the web page offers it).
  schedule       Rotate all on a schedule: monthly, quarterly (every three months) or off, the regular one; --at
                 YYYY-MM-DDTHH:MM once, at that time; show (the default) what is set. The same schedules as the
                 Secrets tab and Jenkins (Command centre > Schedules), so nothing runs twice.
  rotate --due   every one that is due (every 90 days: EAX_ROTATE_PASSWORD_DAYS). A schedule runs this every night at
                 03:17 (System Admin > Commands > Schedules). A laptop keeps its passwords unless EAX_ROTATE_ON_LAPTOP=on.
                 What needs a person (the break-glass password, the mail server's, Keycloak's admin) is never rotated
                 here: the admins are alerted at 30, 14 and 7 days (System Admin > Alerts and > Secrets).
  set KEY        a value you type (after changing it where it is also kept, e.g. the mail server).
  fill           the settings a newer release added, put at the end of the config file (a password made strong
                 and random on a server). eax up does this first, so an update needs no hand editing.
  push --to file:<path>     a copy of every value in a file outside the installation, readable by its owner only.
  pull --from file:<path>   the values back from such a file (a dated copy of the config file first); then restart.
Every restore of the databases and every DR sets each database login's password to the config file in use (R6-D1).

### certs [list|check|renew|revoke|switch|front] [WHAT] [--force] [--authority] [--cert FILE] [--key FILE] [--chain FILE]
> Certificate mode: EA Explorer's own certificates, which the services sign in to the database with.
With EAX_AUTH_MODE=certificate the setup service makes EA Explorer's own certificate authority and a certificate for
each service at every start, on this machine, in the Docker volume eax-certs: never in a backup or a DR pack (a DR copy
makes its own). The database then accepts only TLS, each service by its certificate, only for its own logins.
  list           every certificate: who issued it, until when (the default).
  check          each running service: the user it runs as, and whether it can read its own key (a service that
                 cannot never reaches the database).
  renew          each one that is due made again (two-thirds of its 30 days gone: EAX_CERT_DAYS); a schedule runs this
                 every night at 02:41. --force: every one now. --authority: a new authority and every certificate with
                 it (about every ten years; the database and the services are made again).
  revoke WHAT    a service's certificate refused at once and a new one issued (WHAT: api, library, views,
                 keycloak, reports or dms).
  switch WHAT    how the services sign in, certificate or password (EAX_AUTH_MODE), remembered for the next clean
                 restart; then eax restart. Also System Admin > Secrets (Switch to certificates or passwords).
  front [show]   the front door's certificate (the one people's browsers see), in both modes.
  front install --cert FILE --key FILE [--chain FILE]   your organisation's certificate from files on this machine:
                 checked as System Admin > Secrets checks an upload, the one in use kept, reloaded with no restart.
  front undo     the certificate in use before the last one put back.
$ {eax} certs
$ {eax} certs revoke api
$ {eax} certs switch certificate
$ {eax} certs front install --cert ea.crt --key ea.key --chain chain.pem

### jenkins [up|down|status|pipelines|agent|stop-agent]
> Jenkins: a pipeline for every eax command and DR tool, run with a click (R6.6-J1).
Jenkins runs in its own stack beside EA Explorer, at http://127.0.0.1:8088 on this machine. You sign in with its own
account (eax jenkins up prints it), whatever state EA Explorer is in; EAX_JENKINS_SIGNIN=keycloak signs in with EA
Explorer instead (Super Admins and IT Admins), the own account kept for when Keycloak is down. up waits until Jenkins
answers and, when it does not, says why (its log's own words; all of it in work/jenkins/start.log).
The pipelines are written from this help, so a new command gets a pipeline by itself. A small agent on this machine
(port 8091, its own token) runs each command exactly as typed here. A pipeline that changes everything (a restore, an
update, a wipe, a DR tool) asks for the installation's name before it runs. No job is ever stopped without a person.
  up         Jenkins and the agent started, the pipelines written (the default).
  down       both stopped; the jobs' history is kept.
  status     whether each runs, and the address.
  pipelines  the pipelines written again (after an update).
  agent      the agent, in this window (up starts it in the background).
  stop-agent the agent stopped (down and cleanup do this too). After a clean-run, eax jenkins up again: the
             config file and its tokens are new.
$ {eax} jenkins up
$ {eax} jenkins status

guides are on System Admin > Setup and in Jenkins; the written ones are docs/guides/<guide>.md.
  (none)        the guides, with what each is for.
  <guide>       that guide, guided. --yes runs every step's command in turn (a step that changes everything still
                needs --confirm <installation name>).
  external-db --host H [--port 5432] [--admin-user eax_admin]   EA Explorer on your own PostgreSQL server: tested
                before it is saved; --dba shows the command your DBA runs (deploy/external-db/prepare.sql).
$ {eax} setup
$ {eax} setup server
$ {eax} setup external-db --host db.example.org

### access [admins|reset-password|unlock|mfa-off] [USER] [--all] [--yes]
> Gets an administrator back in, from the machine: a new password, the account unlocked, or MFA removed.
Only for the administrators (the first admin and anyone with the Super Admin or IT Admin role in Keycloak), only to get
back in: people and their roles are managed in EA Explorer and Keycloak. It works inside Keycloak's container, nothing
over the network. USER: the first admin when not given.
  admins           the administrators and whether each is enabled (the default).
  reset-password   a new temporary password, shown once; it must be changed at the next sign-in.
  unlock           the account enabled and its lock after wrong passwords lifted.
  mfa-off          the authenticator removed (a lost phone) and no new one asked for, unless the multi-factor
                   setting wants this person to have one. With --all: multi-factor sign-in off for everyone (the
                   setting set to off, every authenticator removed, nobody asked); asks you to type OFF unless --yes.
$ {eax} access
$ {eax} access reset-password eaadmin
$ {eax} access unlock eaadmin
$ {eax} access mfa-off --all

### settings [parts|export|import|copies|undo] [FILE] [--parts LIST] [--yes]
> Exports or imports the settings and admin configuration as one file, the parts you choose.
The same file as System Admin > Settings import and export: System settings, branding, alerts, keep-for rules, report
audiences, webhooks, pairings' settings, the banner, the IP allow lists and the schedules. Never content, people, a
password, key or certificate. An import first shows every difference and changes nothing; --yes keeps a safety copy,
then takes every difference in those parts (the screen lets you tick them one by one). A file from a newer release is
refused. Nothing is ever removed by an import.
  parts     the parts a file carries.
  export    the settings written to FILE (--parts system,branding: only those).
  import    the differences with FILE shown; with --yes taken.
  copies    the safety copies kept before each import.
  undo      the settings a safety copy kept put back (FILE: the copy's id, from copies).
$ {eax} settings export work/exports/settings.json
$ {eax} settings import work/exports/settings.json --parts system,alerts
$ {eax} settings undo 2c6f0d0e-5e1a-4c43-9d0c-3f1f2c7e6b1a

### trust [--remove]
> Makes the browser trust EA Explorer's local certificate (no more warnings on https://localhost).
[win]It adds work/data/tls/ca.crt to your Windows trusted root certificates.
[unix]It adds work/data/tls/ca.crt to this computer's trusted certificates (macOS: your login keychain; Linux: it
[unix]prints the commands, which need sudo).
Run it once after the first start: clean-run and clean-restart keep the certificate. --remove takes EA Explorer's
certificates out again.
$ {eax} trust
$ {eax} trust --remove

### allow [show|clear|add|remove] [PLACE] [ADDRESS] [NAME]
> The IP allow lists from this machine: who may reach EA Explorer, place by place.
Normally set on System Admin > Security (R5.2). Places: site (everything: the screens, the API, Reports, Documents),
signin (the sign-in pages), admin (System Admin's API), mcp (AI), machine (the client-certificate port). An empty list
lets everyone in. This machine (127.0.0.1) and EA Explorer's own containers are always allowed. Use it when a list
shuts out the people who would change it: clear empties every list at once. Each change is tested by nginx first and
taken without a restart.
$ {eax} allow
$ {eax} allow clear
$ {eax} allow add site 10.20.0.0/16 head office

## Site and deploy

### init [laptop|server] [--certificate|--password] [--hostname NAME]
> Creates the config file work/eaexplorer.env and the work folders. Never overwrites a config file.
Made from the template for the deployment kind (laptop if not given). On a laptop every password is P^55w0rd1234&, as
before; on a server every password and key is made here, strong and random (R6-C1). --certificate or --password says
how the services sign in to each other (see certs); with neither, the choice made last time on this machine, else it
asks, else a laptop uses passwords and a server certificates.
A server asks for the base folder for all the data (EAX_DATA_ROOT, /srv/eax if nothing is typed; R5.4): a folder
for each kind goes under it (see folders). A laptop keeps its Docker volumes and work/ unless EAX_DATA_ROOT is set.
$ {eax} init
$ {eax} init server --certificate --hostname ea.example.org

### hostname [show|set] [NAME]
> The name people open EA Explorer at (EAX_HOSTNAME), with reports.NAME and docs.NAME beside it.
Your certificate must cover all three, and each needs a DNS record pointing at this machine; Keycloak signs people in at
that name. A laptop uses localhost. Moving to a DR site is pointing the name at the other machine, so bookmarks keep
working. set changes it (a dated copy of the config file first); then eax restart. init --hostname sets it at the start;
a server's init asks for it.
$ {eax} hostname
$ {eax} hostname set ea.example.org

### folders [show]
> Where the data lives: the base folder and a folder for each kind, where each is and the space free.
One base folder for all the data (EAX_DATA_ROOT in work/eaexplorer.env, R5.4): under it databases, documents, logs,
backups, imports, exports, certificates and reports. Mount whatever you want onto any of them (the logs and the
documents on a network share, the databases on the local disk): EA Explorer does not decide what goes where. A setting
of its own (EAX_DATA_DIR, EAX_DOCS_DIR, EAX_LOGS_DIR, EAX_BACKUP_DIR, EAX_IMPORT_DIR, EAX_EXPORT_DIR, EAX_TLS_DIR,
EAX_REPORTS_DIR) that names a path puts that kind elsewhere. On Windows the databases stay in their Docker volume
(PostgreSQL cannot run on a Windows folder). up, run and create make any folder that is missing and check each one
first: a base folder that is not there, or a folder that cannot be written, stops the start and says why; where a
folder is (this machine's own disk or a mount) never does. Without EAX_DATA_ROOT nothing changes.
$ {eax} folders

### deploy [--console|--web] [--kind laptop|server] [--plan] [--yes]
> Guided deployment: this laptop, or a server (here or over SSH, wherever it runs).
The deployment wizard (D498). It first asks whether to carry on here in the console or in a web page it opens in your
browser (served by eax itself, before EA Explorer is up); --console or --web skip that question. Then it asks where:
  laptop         this computer: makes the config file if there is none, starts EA Explorer, checks it is healthy.
  server         a Linux server: this one, or another one over SSH from here (a user who may use sudo, signed in
                 with your SSH key). Docker is installed if it is missing; the release is downloaded onto it.
A machine in any cloud is a server: make it there, then deploy to it over SSH (no platform-specific code, D746).
For a server it makes the config file with every password generated and how the services sign in (certificate or
password; the certificates are made on the server itself, never here), your certificate or a self-signed one, starts
EA Explorer, checks it is healthy and shows the address and the first sign-in. It can also move an existing
installation there from one of its infrastructure backups. Every step is in work/logs/eax-<time>-deploy.log (passwords
masked); a step that fails asks: retry, back to the answers, or quit.
  --plan         show every step and every command it would run, and run nothing.
  --kind K       answer the first question; --answers file.json or --set key=value answer others (the answers'
                 names are shown before it starts); --yes runs without asking (every answer given or default).
Not set up yet? The installer downloads EA Explorer first and then runs this: see docs/deployment.md.
$ {eax} deploy
$ {eax} deploy --web
$ {eax} deploy --console --kind aws --plan
$ {eax} deploy --console --kind server --set where=ssh --set ssh_target=ubuntu@203.0.113.10 --set hostname=ea.example.org

## Help and documentation

### help [command|--all]
> This overview; one command in full, with examples; or --all for every command in full.
Also: {eax} <command> --help (or -h, or /?). help --groups lists the groups of commands; help --group N shows the
commands of group N in full; help --search <word> shows in full every command whose help has the word (eax
document's console uses all three).
$ {eax} help stop
$ {eax} help --all

### screen
> A full-screen eax in the style of Turbo Pascal: menus, a dialog per command, a live dashboard.
Also what {eax} with no command opens on a terminal (piped or in a script it prints this overview, as before). The
menu bar has the groups below: F10 or Alt and a group's letter opens one, the arrows move, Enter picks, Escape closes;
the mouse works too. A command's dialog is made from this help: choices as lists (or type one), flags as tick boxes,
values as fields, and the whole command is shown as you fill it; Run or Cancel. The middle of the screen shows each
container in its state's colour and the free disk space, refreshed every 5 seconds. A command that only prints (status,
backups, services, ...) shows its output in a window; one that asks questions or follows logs switches to the plain
terminal and comes back with Enter (Alt+F5 shows that screen too). F1 Help, F5 Refresh, Alt+X Exit. Textual is
fetched once into work/tools/pylib (nothing installed elsewhere); offline the first time, in an old console, or with
EAX_SCREEN=off in the environment, the numbered menu opens instead (R3.1).
$ {eax}
$ {eax} screen

### menu
> A numbered menu of every command by group: pick one, answer its questions, see it, then run it.
What {eax} screen falls back to when the full screen cannot open. Each option of the command is asked for in turn;
Enter leaves an optional one out. The whole command is shown before it runs, and it runs only when you answer y. Typing
a command that does not exist shows the nearest ones (did you mean).
$ {eax} menu

### site [build|check|shots|pdfs] [--only PAGES] [--missing]
> Makes the website and its pictures, and prints the 24 guides as PDFs.
The website is a folder for each release, services/web/public/site/<version>: EA Explorer serves them at /site/
(it opens the newest), and the folder can be copied anywhere and published as it is. Every How do I page names the screen it is done on; shots opens each of those screens
on this installation, signed in as the first Super Admin (eaadmin unless set), and keeps a picture of it in docs/site/shots.
It signs in and opens pages (and the tab or dialog a page names): nothing is saved. It is not part of the tests. Use it on a laptop or test
installation with the demo data, then make the website again (shots does that itself).
  build     the website made again from docs/site, docs/guides and releases.
  check     the same in memory: what is wrong (a link to nowhere, a page with no screen); nothing written.
  shots     the pictures taken (--only: those pages, by file name; --missing: only those not taken yet; --width and
            --height: the browser window, 1280 by 800 unless given).
  pdfs      the 24 printed guides as PDFs in documents/ (in git), then the website again with them under
            Printed guides (--only: those guides, by id, e.g. 01-overview). Run shots first: the PDFs use its pictures.
$ {eax} site build
$ {eax} site shots --missing
$ {eax} site shots --only back-up-now,add-an-entity
$ {eax} site pdfs
$ {eax} site pdfs --only 14-emergency

turn colours off; output sent to a file or another program is always plain.
